SECCIÓN 1 — Investigación

3. Qué es Android

Android es un sistema operativo para dispositivos móviles construido sobre el núcleo de Linux, desarrollado hoy por Google y la Open Handset Alliance. Nació en 2003 como una empresa independiente —Android Inc., de Andy Rubin— que Google compró en 2005; la primera versión pública es de 2008.

Lo que explica casi todo lo demás es que Android no es Linux con otra cara: es una pila de capas donde cada una resuelve un problema distinto. 

┌─────────────────────────────────────────────┐
│  Aplicaciones        la tuya, y las de serie │
├─────────────────────────────────────────────┤
│  Marco de trabajo    Activity, Service,      │
│  (Java/Kotlin API)   ContentProvider…        │
├─────────────────────────────────────────────┤
│  Bibliotecas         ART (ejecuta el código) │
│  nativas + ART       SQLite, OpenGL, Media   │
├─────────────────────────────────────────────┤
│  HAL                 abstrae el hardware:    │
│                      cámara, sensores, GPS   │
├─────────────────────────────────────────────┤
│  Núcleo Linux        procesos, memoria,      │
│                      controladores, permisos │
└─────────────────────────────────────────────┘

La capa de abstracción del hardware (HAL) es la que permite que la misma aplicación funcione en un teléfono de gama baja y en uno de gama alta con cámaras distintas: la aplicación pide «una foto», no «esta cámara concreta».

4. Qué es un APK

APK es Android Package: el archivo que se instala en el dispositivo. Por dentro es un ZIP con una estructura fija.

Dentro del APKQué es
AndroidManifest.xmlLa declaración: nombre, versión, permisos, actividades y cuál se abre primero
classes.dexEl código compilado a bytecode DEX, que es lo que ART ejecuta
resources.arscLos recursos compilados: textos, colores, medidas
res/Imágenes y diseños de pantalla
lib/Bibliotecas nativas, una carpeta por arquitectura
META-INF/La firma digital

Todo APK va firmado, y la firma hace dos cosas. Identifica a quien lo publicó —no por su nombre, sino porque la clave es siempre la misma— y permite que el sistema compruebe que el archivo no fue modificado después. De ahí sale una regla con consecuencias prácticas: una actualización solo se instala sobre una aplicación firmada con la misma clave. Perder la clave de firma significa no poder volver a actualizar la aplicación nunca; hay que publicarla con otro identificador y pedirle a cada usuario que la instale de cero.

Desde 2021, Google Play recibe en cambio un AAB (Android App Bundle), y es Play quien genera un APK a medida de cada dispositivo. La diferencia importa: el AAB se sube a la tienda, el APK se instala. Para una aplicación interna como la de AA2-EV02, que se instala a mano, el APK sigue siendo el formato.

5.1 Tres números que se confunden todo el tiempo

Nivel de APIQué significaQué decide
minSdkLa versión más antigua que puede instalarlaA cuánta gente llegas
targetSdkLa versión contra la que se probóQué comportamientos nuevos se te aplican
compileSdkLas API disponibles al compilarQué puedes escribir

Bajar minSdk amplía el público y obliga a comprobar en tiempo de ejecución si una función existe. Subir targetSdk es obligatorio para publicar en Play y activa restricciones nuevas: una aplicación con targetSdk viejo conserva permisos que ya no se conceden. Es la tensión central de mantener una aplicación Android.

6. Lenguajes

LenguajeSituación
KotlinEl recomendado por Google desde 2019. Tipos que distinguen lo que puede ser nulo de lo que no, corrutinas para el trabajo en segundo plano, menos código repetido
JavaSigue funcionando. Millones de líneas en producción, y es el que se ha usado en GA7
C / C++ (NDK)Solo para lo que necesita velocidad: motores de juego, procesamiento de señal
Dart, JavaScriptMultiplataforma (Flutter, React Native). No son Android nativo

Los dos primeros conviven en el mismo proyecto porque ambos compilan al mismo bytecode DEX. Una clase Kotlin puede llamar a una Java y al revés, sin puente ni conversión.

Qué se usará en AA2-EV02, y por qué. El proyecto móvil de MONK GRAIN se escribirá en Kotlin. El motivo no es que sea lo recomendado: es que el tipo que distingue lo nulo de lo no nulo resuelve en el compilador justo el error que más aparece al consumir una API —un campo que llega vacío y nadie lo previó—. En Java ese error aparece en el teléfono del usuario; en Kotlin, al compilar.

8. Android multiusuario

Android soporta varios usuarios en un mismo dispositivo, cada uno con sus aplicaciones, sus datos y sus cuentas. Hay tres figuras distintas:

FiguraQué es
Usuario completoUn espacio independiente. Instala sus aplicaciones, no ve las de los demás
Perfil restringidoComparte las aplicaciones del dueño con límites. Pensado para menores
Perfil de trabajoSepara lo laboral de lo personal en el mismo teléfono. La empresa administra solo ese perfil

El mecanismo es sencillo y contundente: cada usuario tiene su propio directorio de datos (/data/user/0/, /data/user/10/…) y el núcleo impide que un proceso lea el del otro. No es una cortina en la interfaz, es un permiso del sistema de archivos.

Para quien desarrolla, la consecuencia práctica es que la misma aplicación puede estar instalada dos veces con datos distintos. Una aplicación que guarde una sesión suponiendo que hay un solo usuario se comportará de forma extraña cuando la abra el segundo. Es el mismo error de fondo que guardar estado global en un servidor web que atiende a varias personas.

9. Mínimo privilegio

Es el principio que atraviesa toda la seguridad de Android: cada aplicación recibe lo mínimo para funcionar, y nada más.

9.1 Cómo se implementa

MecanismoCómo funciona
Un UID por aplicación Android aprovecha los usuarios de Linux: cada aplicación instalada recibe su propio identificador de usuario, y sus archivos pertenecen a ese UID. Una aplicación no puede leer los datos de otra porque el sistema de archivos no se lo permite
Proceso aislado Cada aplicación corre en su propio proceso con su propia instancia de ART. Si una se cae, no arrastra a las demás
Permisos declarados Lo que necesita acceso fuera de su caja se declara en el manifiesto. Lo no declarado, no existe para esa aplicación
Permisos peligrosos en tiempo de ejecución Desde Android 6, cámara, ubicación, contactos y micrófono se piden al usar, no al instalar, y el usuario puede negarlos o concederlos solo esta vez
SELinux Control de acceso obligatorio que limita incluso a los procesos del sistema. Una aplicación comprometida no hereda todo el dispositivo
Alcance del almacenamiento Desde Android 10, una aplicación ve sus archivos y lo que el usuario elija, no la tarjeta entera

Es el mismo principio que gobierna el backend de MONK GRAIN. Allí los endpoints no preguntan «¿eres administrador?» sino «¿tienes el permiso product.create?», y hay 24 permisos en vez de cuatro roles con poderes amplios. La idea de fondo es idéntica: conceder lo mínimo y nombrarlo. La diferencia es quién concede —el usuario del teléfono en Android, un administrador en la plataforma—.

9.2 Lo que esto significa al escribir la aplicación

  • Pedir un permiso cuesta usuarios. Cada diálogo es una oportunidad de que digan que no y de que desconfíen. La aplicación de AA2-EV02 solo necesitará INTERNET, que ni siquiera abre diálogo.
  • Hay que programar para el «no». Un permiso puede negarse, o concederse «solo esta vez». La aplicación tiene que seguir siendo útil sin él, no quedarse en una pantalla en blanco.
  • Los datos sensibles no van en almacenamiento compartido. Un token de sesión va en el almacenamiento privado de la aplicación o, mejor, cifrado.

10. Componentes esenciales de una aplicación

Son cuatro, y todos tienen algo en común: el sistema los crea y los destruye, no la aplicación. Esa inversión explica casi todos los errores de principiante en Android.

ComponenteQué esEjemplo en MONK GRAIN móvil
Activity Una pantalla con la que el usuario interactúa La lista de lotes; el detalle de un lote
Service Trabajo sin interfaz, que sigue aunque se cierre la pantalla Subir la foto de un lote mientras el caficultor hace otra cosa
Broadcast Receiver Reacciona a avisos del sistema o de otras aplicaciones Volver a intentar el envío cuando regrese la conexión
Content Provider Comparte datos con otras aplicaciones, de forma controlada No se usará: los datos del lote no se comparten fuera

10.1 El ciclo de vida de una Activity, y por qué importa

              onCreate()      se crea
                   ↓
              onStart()       va a verse
                   ↓
              onResume()      está al frente  ◄───┐
                   ↓                              │
            [el usuario usa la app]               │
                   ↓                              │
              onPause()       pierde el frente ───┘
                   ↓
              onStop()        ya no se ve
                   ↓
              onDestroy()     se destruye

Lo que convierte esto en algo más que un diagrama es que el sistema puede destruir una Activity para recuperar memoria y recrearla después, y también lo hace al girar el teléfono. Si el estado vive en una variable de la Activity, girar la pantalla lo borra.

Es el error clásico de Android: la aplicación funciona, el usuario gira el teléfono, y el formulario a medio llenar desaparece. Se evita guardando el estado donde sobreviva —hoy, un ViewModel—, no recordando poner el teléfono derecho.

10.2 El manifiesto y los intents

AndroidManifest.xml declara los componentes. Lo que no está declarado, no existe para el sistema: una Activity sin su entrada no se puede abrir, aunque la clase esté compilada dentro del APK. 

<manifest xmlns:android="http://schemas.android.com/apk/res/android">

    <!-- Lo único que necesita la app de MONK GRAIN: hablar con la API.
         INTERNET es un permiso normal, no peligroso: se concede al
         instalar y no abre ningún diálogo al usuario. -->
    <uses-permission android:name="android.permission.INTERNET" />

    <application android:label="MONK GRAIN">
        <activity
            android:name=".MainActivity"
            android:exported="true">

            <!-- Este filtro es lo que pone el icono en el lanzador.
                 Sin él la app se instala y no hay forma de abrirla. -->
            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.intent.category.LAUNCHER" />
            </intent-filter>
        </activity>
    </application>
</manifest>

Los componentes se comunican con intents, que son mensajes. Un intent explícito nombra a quién va dirigido; uno implícito describe lo que se quiere —«abrir esta dirección»— y el sistema ofrece quién puede hacerlo. El implícito es lo que permite que compartir una foto muestre la lista de aplicaciones capaces de recibirla, sin que ninguna conozca a las otras.

Los textos van en strings.xml, no dentro del diseño. No es burocracia: es lo que permite traducir la aplicación añadiendo values-en/strings.xml sin tocar una sola pantalla. Es la misma idea que messages.properties en el módulo de Spring de GA7-AA3.

13. La actividad principal

MainActivity.kt:

package co.monkgrain.hola

import android.os.Bundle
import android.widget.TextView
import androidx.appcompat.app.AppCompatActivity

/**
 * La primera pantalla de la aplicación.
 *
 * Hereda de AppCompatActivity y no de Activity a secas: AppCompat trae las
 * funciones nuevas a las versiones viejas de Android, que es lo que permite
 * poner minSdk en 24 sin renunciar a lo de hoy.
 */
class MainActivity : AppCompatActivity() {

    /**
     * El sistema llama a este método al crear la pantalla, y también al
     * recrearla —por ejemplo, al girar el teléfono—. Por eso todo lo que
     * dibuja va aquí y no en el constructor: el constructor corre una vez,
     * `onCreate` corre cada vez que hay que volver a dibujar.
     *
     * `savedInstanceState` trae el estado guardado si es una recreación, y
     * es `null` la primera vez. De ahí el tipo `Bundle?`, con interrogante:
     * Kotlin obliga a decidir qué pasa cuando no hay nada.
     */
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        // Conecta la pantalla con su diseño en XML.
        setContentView(R.layout.activity_main)

        // R es una clase que Android genera al compilar los recursos: por eso
        // un error en el XML aparece aquí como «no se encuentra R».
        val mensaje = findViewById<TextView>(R.id.mensaje)
        mensaje.text = getString(R.string.saludo)
    }
}

res/layout/activity_main.xml:

<?xml version="1.0" encoding="utf-8"?>
<androidx.constraintlayout.widget.ConstraintLayout
    xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:app="http://schemas.android.com/apk/res-auto"
    android:layout_width="match_parent"
    android:layout_height="match_parent">

    <!-- El identificador es lo que permite encontrarlo desde el código
         con findViewById. Sin id, la vista existe y es inalcanzable. -->
    <TextView
        android:id="@+id/mensaje"
        android:layout_width="wrap_content"
        android:layout_height="wrap_content"
        android:textSize="22sp"
        app:layout_constraintTop_toTopOf="parent"
        app:layout_constraintBottom_toBottomOf="parent"
        app:layout_constraintStart_toStartOf="parent"
        app:layout_constraintEnd_toEndOf="parent" />

</androidx.constraintlayout.widget.ConstraintLayout>

res/values/strings.xml:

<resources>
    <string name="app_name">Hola MONK GRAIN</string>
    <string name="saludo">¡Hola! Soy Eliana Chacon</string>
</resources>

Por qué sp y no dp para el texto. dp es independiente de la densidad de la pantalla; sp además respeta el tamaño de letra que el usuario configuró en el sistema. Usar dp en texto ignora a quien necesita la letra grande para leer.

16. Conclusión

Android es Linux aprovechado de una forma concreta: cada aplicación es un usuario del sistema, con sus archivos protegidos por los permisos del sistema de archivos y no por una cortina en la interfaz. De ahí salen el aislamiento entre aplicaciones, el soporte multiusuario y el mínimo privilegio — tres cosas que parecen separadas y son el mismo mecanismo visto desde ángulos distintos.

Para quien desarrolla, lo que más cambia respecto de una aplicación web es que el sistema manda: crea y destruye las pantallas cuando le conviene, y concede o niega los permisos según lo que diga el usuario. Programar para Android es, en buena medida, programar para que eso no rompa nada.
